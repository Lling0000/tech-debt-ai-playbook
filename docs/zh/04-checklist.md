# 04. 小白检查清单

这是一份可以直接照着用的检查清单。

当你准备让 AI 改代码、重构系统、处理技术债时，先过一遍。

## 一、先别急着改

问自己：

- 这个改动的目标是什么？
- 是修 bug、加功能、提性能，还是还技术债？
- 哪些行为不能变？
- 哪些用户或系统会受影响？
- 最坏情况是什么？

如果你说不清目标，不要急着让 AI 写代码。

## 二、找最容易先崩的地方

重点看：

- 核心业务链路
- 没有测试的代码
- 被很多地方调用的代码
- 数据库迁移
- 权限逻辑
- 缓存逻辑
- 异步任务
- 第三方依赖
- 状态机

可以问 AI：

```text
请先不要改代码。
请帮我找出这个模块最可能回归的地方，并按风险从高到低排序。
```

## 三、先补测试

测试不一定一开始就很完美。

小白可以先补三类：

- 正常路径测试：用户正常操作能不能成功
- 异常路径测试：错误输入、没权限、数据不存在时会怎样
- 旧行为测试：重构前已有行为是否保持不变

可以问 AI：

```text
请根据当前代码补 characterization tests。
目标是固定现在的外部行为，而不是改变实现。
```

## 四、控制 AI 的改动范围

不要只说：

```text
帮我优化一下。
```

改成：

```text
请只修改这些文件：
- ...

要求：
- 保持 public API 不变
- 不改变返回字段
- 不引入新依赖
- 不删除旧兼容逻辑
- 先补测试再改实现
- 最后说明风险点
```

## 五、准备影子替代

如果改动很危险，问：

- 新旧逻辑能不能同时运行？
- 新逻辑能不能先只记日志，不影响用户？
- 能不能对比新旧输出？
- 能不能用 feature flag 开关？
- 出问题能不能马上关掉？

可以问 AI：

```text
请为这个改动设计 shadow mode。
旧逻辑继续服务用户。
新逻辑只计算并记录差异。
请给出开关、日志字段、指标和回退方式。
```

## 六、上线前检查

上线前问：

- 测试跑过了吗？
- 有监控吗？
- 有告警吗？
- 有日志能定位问题吗？
- 有 feature flag 吗？
- 能回滚吗？
- 回滚会不会造成数据不一致？
- 谁会第一时间发现问题？

## 七、一个最小模板

你可以把下面这段直接复制给 AI：

```text
我要修改这个模块，但我不想破坏旧行为。

请按顺序做：
1. 先总结这个模块的外部可观察行为。
2. 列出最可能回归的地方。
3. 设计最小测试集。
4. 说明哪些地方需要 shadow mode 或 fallback。
5. 在不改变 public API 的前提下做最小改动。
6. 最后列出我上线前应该检查的指标和回滚方案。

限制：
- 不要引入新依赖，除非先说明理由。
- 不要大规模重构。
- 不要改变返回字段。
- 不要删除兼容逻辑。
```

## 最后记住一句

> AI 可以帮你写代码，但不能替你承担工程判断。

你越懂系统哪里会坏，越懂技术栈的失败模式，越能让 AI 成为你的执行力。
