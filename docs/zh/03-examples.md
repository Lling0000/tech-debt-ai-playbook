# 03. 实例：从会崩的地方开始

这一章用几个简单例子，把前面的观念落到真实场景里。

## 例子一：登录接口重构

### 场景

你有一个旧登录接口，代码很乱。

AI 建议你重构成更清晰的服务结构。

### 容易先崩的地方

- 返回字段被老版本 App 依赖
- 冻结用户、注销用户、未绑定手机号用户的逻辑被改坏
- token 过期时间变化
- 登录失败次数风控失效
- 客服后台仍然调用旧接口

### 不稳的做法

```text
直接让 AI 重写登录模块，然后上线。
```

这很危险，因为你不知道旧系统里有哪些隐式规则。

### 更稳的做法

1. 先记录旧接口行为。
2. 补测试覆盖正常登录、错误密码、冻结用户、旧用户。
3. 新登录逻辑放在 feature flag 后面。
4. shadow mode 中同时运行旧逻辑和新逻辑。
5. 对比新旧输出差异。
6. 小流量灰度。
7. 保留快速回退。

### 可以这样驱动 AI

```text
请不要直接重构。
先列出登录接口的外部可观察行为。
然后设计 characterization tests。
新实现必须保持响应字段兼容。
请给出 shadow mode 的接入点和差异日志字段。
```

## 例子二：订单状态机修改

### 场景

订单有这些状态：

```text
created -> paid -> shipped -> completed
created -> canceled
paid -> refunded
```

现在你想新增一个状态：

```text
paid -> preparing -> shipped
```

### 容易先崩的地方

- 老代码假设 paid 后面只能是 shipped 或 refunded
- 报表统计不认识 preparing
- 客服后台无法展示新状态
- 定时任务把 preparing 当成异常状态
- 移动端旧版本没有对应文案

### 不稳的做法

```text
只改数据库枚举和后端状态流转。
```

这样可能后端能跑，但其他系统开始出错。

### 更稳的做法

1. 搜索所有读取订单状态的地方。
2. 给状态流转补测试。
3. 给报表、后台、定时任务补兼容。
4. 新状态先只对内部订单开放。
5. 指标正常后再扩大范围。

### 可以这样驱动 AI

```text
请帮我分析新增 preparing 状态的影响面。
不要先写代码。
请列出所有可能读取订单状态的模块、需要补的测试、以及必须保留兼容的地方。
```

## 例子三：数据库字段迁移

### 场景

你想把 `name` 字段拆成：

```text
first_name
last_name
```

### 容易先崩的地方

- 旧服务还在写 `name`
- 新服务只读 `first_name` 和 `last_name`
- 历史数据没有拆分
- 回滚后数据结构不兼容
- 搜索、导出、报表仍然依赖 `name`

### 不稳的做法

```text
直接删除 name 字段，新增 first_name 和 last_name。
```

这会让旧代码直接崩掉。

### 更稳的做法

可以分三步：

```text
expand -> backfill -> contract
```

意思是：

1. expand：先加新字段，不删旧字段。
2. backfill：把历史数据补到新字段。
3. contract：确认所有服务都不依赖旧字段后，再删除旧字段。

### 可以这样驱动 AI

```text
请设计一个可回滚的数据库字段迁移方案。
要求分为 expand、backfill、contract 三步。
旧字段在迁移稳定前不能删除。
请列出每一步的测试和回滚方式。
```

## 例子四：前端页面重构

### 场景

一个页面太乱，你想让 AI 帮你拆组件。

### 容易先崩的地方

- 表单默认值变化
- 提交参数变化
- loading 状态丢失
- 错误提示文案变化
- 埋点丢失
- 权限按钮展示条件变化
- 移动端布局坏掉

### 不稳的做法

```text
让 AI 按最佳实践重构整个页面。
```

### 更稳的做法

1. 先列出页面行为。
2. 补交互测试或截图对比。
3. 先拆纯展示组件。
4. 再拆表单逻辑。
5. 最后拆请求和状态管理。
6. 每一步都跑测试和人工预览。

### 可以这样驱动 AI

```text
请只拆纯展示组件，不改变请求逻辑和表单提交逻辑。
保持 DOM 文案、埋点字段、权限判断不变。
请列出你认为可能变化的用户可见行为。
```

## 本章总结

好的工程动作通常不是：

```text
大改一把，然后祈祷没问题。
```

而是：

```text
先知道哪里会坏，再用测试保护它，然后小步替换，最后可观测地上线。
```
