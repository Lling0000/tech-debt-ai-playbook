# 00. 写在前面

这份文档不是教你“哪个技术栈最好”。

它想帮你建立一种更稳的工程直觉：

> 不要先问用什么技术栈。  
> 先问哪里会先崩，怎么发现，怎么回退。

很多小白刚开始写代码时，会以为厉害的工程师厉害在会更多框架、更多语言、更多工具。

这些当然有用，但真正拉开差距的，往往不是“知道更多名字”，而是知道：

- 哪些地方看起来简单，其实最容易出事故
- 哪些代码能跑，但以后很难改
- 哪些重构看起来优雅，但会破坏旧行为
- 哪些 AI 生成的代码看起来完整，实际上没有考虑线上风险
- 哪些测试必须先补，不然改动就是赌博

## 一个小故事

假设你有一个登录接口。

它现在很旧，代码也很乱。AI 看完以后说：

```text
这个模块职责混乱，建议重构为 auth service、token service、user service 三层。
```

听起来很合理。

但如果你直接照做，可能会踩到这些坑：

- 老版本 App 还依赖旧返回字段
- 某些用户没有手机号，但旧逻辑允许登录
- 登录失败次数会触发风控
- token 过期时间被另一个服务假设为 7 天
- 客服后台也在调用同一个接口

这些东西，AI 不一定知道。

你真正应该先做的是：

1. 记录现在登录接口的外部行为。
2. 补测试，确保旧行为被固定下来。
3. 找出最危险的改动点。
4. 新逻辑先在旁边跑，只对比结果，不直接影响用户。
5. 确认稳定后，再逐步切流。

这就是工程判断。

## 这份文档的主线

我们会一直围绕一个简单闭环：

```text
识别风险 -> 写测试 -> 小步改动 -> 影子运行 -> 灰度切换 -> 保留回退
```

这个闭环比任何单个框架都重要。

但同时，你越懂某个框架和技术栈里的隐性知识，你越知道风险在哪里。这样你才能给 AI 更清晰的指令，让 AI 帮你执行，而不是让 AI 替你决定。
