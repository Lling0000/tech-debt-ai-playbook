# 01. 核心观念：技术栈不是信仰

## 先说结论

“技术栈不是那么重要”这句话，不是说技术栈知识不重要。

它真正反对的是技术栈崇拜。

错误理解是：

```text
只要换成更先进的技术栈，系统就会变好。
```

更准确的理解是：

```text
技术栈是工具。
系统能不能变好，取决于你是否知道风险在哪里，是否能验证改动，是否能安全回退。
```

## 小白常见误区

很多人一看到项目老、代码乱、技术债多，就会立刻想到：

- 要不要换框架？
- 要不要重写？
- 要不要上微服务？
- 要不要上 Kubernetes？
- 要不要让 AI 全部重构一遍？

这些想法不一定错，但它们太靠后了。

更靠前的问题应该是：

- 现在系统最重要的业务链路是什么？
- 哪些旧行为不能变？
- 哪些地方没有测试？
- 哪些地方一改就可能影响用户？
- 出错以后能不能快速回退？
- 有没有监控能告诉我们真的出错了？

## 什么叫“先崩”

“先崩”就是最容易先出问题的地方。

它可能是：

- 没有测试的核心函数
- 被很多地方调用的公共方法
- 写得很复杂的状态机
- 数据库迁移脚本
- 缓存逻辑
- 权限判断
- 支付、订单、库存、登录这类关键链路
- 依赖第三方服务的地方

如果你不知道哪里先崩，你就不知道测试应该保护哪里。

## 什么叫“先塌”

“先塌”比“先崩”更严重。

有些地方坏了，只是一个按钮不能点。

有些地方坏了，会让整个系统跟着出问题。

比如：

- 登录坏了，所有用户都进不来
- 权限坏了，可能导致数据泄露
- 订单状态错了，后续支付、库存、发货都错
- 数据迁移错了，旧版本服务和新版本服务读到不同结构
- 消息队列重复消费，导致重复扣款或重复发货

这些地方就是承重位置。

工程上最重要的不是先把代码变漂亮，而是先保护承重位置。

## 测试驱动不是死板地先写测试

很多人听到 TDD，也就是 Test Driven Development，会以为它要求你永远先写测试，再写代码。

对小白来说，可以先理解成更简单的一句话：

> 在你改危险代码之前，先用测试描述你不希望被破坏的行为。

如果你要重构登录接口，测试应该先回答：

- 正确密码能不能登录？
- 错误密码会返回什么？
- 被冻结用户会发生什么？
- 没有手机号的旧用户还能不能登录？
- token 格式和过期时间有没有变化？

这些测试不是为了形式感，而是为了防止你把旧系统里重要但隐蔽的行为改没了。

## 影子替代是什么

影子替代，也可以叫 shadow mode。

意思是：

> 新方案先在旁边运行，接收同样的输入，但不直接影响真实用户。

比如旧登录逻辑继续返回结果给用户。

新登录逻辑也同时计算一次，但结果只写日志，用来和旧逻辑对比。

如果新旧结果一致率很高，错误率也正常，再考虑逐步切换。

这样做的好处是：

- 新逻辑提前接受真实流量考验
- 用户不会被新逻辑直接影响
- 你能看到新旧结果差异
- 出问题时不需要紧急回滚，因为新逻辑还没有接管

## 本章总结

技术栈不是信仰。

真正重要的是：

```text
知道哪里危险 -> 用测试固定行为 -> 小步替换 -> 新旧对比 -> 可回退上线
```

如果你能这样思考，AI 就会成为你的工具。

如果你只问“帮我换个更现代的架构”，AI 就可能变成你的方向盘。
